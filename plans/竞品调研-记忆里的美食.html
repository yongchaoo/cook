结论先行

先给判断，再给证据。本轮调研最重要的产出是「三个假设被推翻」。

  1. 产品主体判断成立，但差异化落点要换。「查看菜谱 + 材料清单 + 投稿 + 后台 + 数据库」是行业标配，不构成差异；「记忆叙事 + 视频解析 + 计时器」也分别已有大量玩家。真正没人做的，是把「被遗忘的关键细节」抽象成独立、可检索、可审核、可精选的结构化内容实体，并让它同时连接内容生产管线与 UGC 投稿。差异在内容模型层，不在功能层。
  2. 视频转菜谱已从「设想」变成 2026 年的成熟品类。海外 ReciMe 被第三方估算月流水约 278 万美元、用户约 1,500 万；中文侧谱提 Pullit、Coozi、口袋厨神、一键大厨、拾味记等已覆盖抖音 / 小红书 / B站，开源方案门槛低到「单人周末可完成」。自研解析引擎不再是壁垒。
  3. 「记忆里的美食」这个情感切口也不是空白。下厨房官网有「妈妈的味道」专题 2,316 件作品、「家乡的味道」625 件；已有「味觉记忆馆」「家传菜谱博物馆」「食遇日记」等做家传菜谱、语音录制、味道日记的产品或概念。但它们都是话题标签 / 私人记录本形态，不是「公开可检索的结构化内容库 + 审核发布」。
  4. 计时器是标配，而且我们的「单计时器」结论与市场主流方向相反。下厨房烹饪模式、豆果智能定时、谱提内置计时器 + 灵动岛 / Apple Watch、Kitchen Stories 引导模式、拿手菜小本本一步一屏都已具备；更关键的是云小厨、拿手菜小本本走的是多菜并行、各自独立计时，对应真实的双灶场景。原型 v4 基于「降低压力感」选择单计时器，是 UX 判断而非功能优势，需要单独做一次验证。
  5. 微信小程序形态已被验证可行且成本极低。「拾味记」用腾讯云 ASR + Moonshot Kimi + 云开发异步队列实现抖音视频转菜谱，公开描述称云开发按量计费「成本趋近于零」。这支持架构方案里 A 路线（先不写重后台），但也意味着冷启动速度比技术本身更关键。

三个被推翻的原假设（对应上一版架构方案）

  • 原假设：P3「视频 → 材料与步骤」是后续创新点 → 已是红海初现，应改为接入现成能力。
  • 原假设：「记忆 / 家传菜谱」是独有定位 → 已有多家在做，须收敛到「结构化细节」。
  • 原假设：单一聚焦计时器是体验优势 → 是取舍不是优势，多灶场景存在缺口。

仍然成立的三条架构判断

① 管理后台不做第二个云应用（单环境单库）依然正确，且同类小程序多为单人云开发，更不该拆库；②「被遗忘的细节」独立成表、独立审核的设计依然是空白点；③ 数据库单一事实源 + 小程序只读 published 的内容发布模型，在竞品里普遍缺失（多数是私人记录本，没有审核发布态）。

02

赛道格局：三条线，一个空白区

用「内容结构化 / 自动化程度」×「情感记忆浓度」两个维度定位，右上象限是现有产品没有同时覆盖的区域。

三条线

① 内容库存型（下厨房 / 豆果 / 香哈 / 美食杰）：菜谱量是资产，但流量被抖音、小红书分流，变现长期依赖广告与电商，且电商多次受挫。

② 视频转菜谱型（ReciMe / 谱提 / Coozi / 口袋厨神 / Pluck）：解决「收藏 → 上桌」，是当前增长最快、付费模型最清晰的一条线。

③ 家传记忆型（味觉记忆馆 / 家传菜谱博物馆 / 食遇日记 / 下厨房情感专题）：情感浓度高，但形态是话题标签或私人记录本，缺少结构化与公开检索。

空白区

把 高结构化 与 高情感记忆 同时做到，且带内容审核与发布态、面向公开内容库而非私人本——象限右上没有对应产品。

注：位置为基于公开资料的相对判断，不是量化评分，不用于排名。

竞品图鉴（真实截图）

15 款 App、30 张 App Store 官方宣传截图。点击截图可放大并切换第 2 张；卡片上的版本、评分、评分人数、更新日期均来自官方接口实时采集，未手工填写。

下厨房

A 级
中国区版本 v8.9.72评分 4.8444.2 万 人评分更新 2026-10-23

定位 国内最大 UGC 菜谱社区，约 358–400 万道菜谱，核心机制是「跟做作品」。

  • 强项用料按人数换算（调味非线性递增）、烹饪模式、评论区实操贴士、菜谱生命周期极长；官网已有「妈妈的味道」2,316 件 / 「家乡的味道」625 件作品
  • 短板情感内容只是话题标签，不是结构化字段；无法沉淀「这一次我改了什么」；广告与会员自动续费被反复吐槽；电商（市集 / 线下店 / 预制菜）多次收缩
  • 启示情感需求已被验证，但供给形态停留在「晒作品」。我们要做的是把其中的「家里多做的那一步」抽出来变成可检索字段

懒饭

A 级
中国区版本 v2.5.0评分 4.8815.9 万 人评分更新 2026-10-21

定位 下厨房旗下，面向新手的「零失败」短视频菜谱，1 分钟视频 + 精确到克 / 毫升的用量。

  • 强项直接针对中式菜谱「适量 / 少许」的结构性缺陷；每道菜标总时长与操作时间；按食材找菜谱；语音跟做
  • 短板本质是「学做菜」工具，不能创建自己的菜谱库；无法记录家人口味调整；关键防错贴士仍是自由文本
  • 启示「精确化」已被证明是新手最强卖点，我们的材料清单必须同时保留原文快照（少许）与归一化数值，并明确标注哪些是审核推定值

豆果美食

A 级
中国区版本 v8.2.32评分 4.9019.9 万 人评分更新 2026-09-02

定位 老牌 PGC + UGC 社区，宣称 3 亿用户 / 300 万道菜谱（厂商自述，未独立核验）。

  • 强项菜谱页一键把食材导入买菜清单并自动按品类归类；食材替换建议；智能定时提醒；步骤图质量高
  • 短板部分菜谱仍写「适量」；广告推送较多；记录结构化程度一般；家庭协作能力弱
  • 启示「材料清单 → 采购清单」是已被验证的高频链路，我们的 dish_ingredients 应在 P1 就支持勾选与份量换算，而不是留到后期

香哈菜谱

A 级
中国区版本 v9.8.2评分 4.8823.6 万 人评分更新 2026-08-09

定位 剩余食材反向检索 + 养生体质定制；运营主体香哈股份（833399.NEEQ）是赛道唯一公开财务数据的标的。

  • 强项按现有食材反推菜谱；宣称 100 万+ 原创高清菜谱、1 万+ 原创视频；2026H1 营收同比 +61.53% 并扭亏

美食杰

A 级
中国区版本 v8.2.9评分 4.9020.5 万 人评分更新 2026-03-15

定位 菜谱资料库型，营养分析 + 按现有食材智能组菜。

  • 强项百万级图文 + 视频菜谱；「有什么吃什么」反向匹配最接近我们设想的材料反查
  • 短板工具属性强但社区与情感弱；无 UGC 细节沉淀机制
  • 启示反向检索 + 营养是同质化功能，避免在 MVP 投入；把资源放在别人没有的「细节实体」上

谱提 Pullit

A+B 级
中国区版本 v1.8.0评分 5.0016 人评分更新 2026-11-15

定位 「一个属于你自己的菜谱管理器，而不是又一个让你搜别人菜谱的 App」。中文侧功能完整度最高的视频转菜谱产品。

  • 强项支持九平台（小红书 / 抖音 / B站 / 下厨房 / 视频号 / YouTube / TikTok / IG / Pinterest）；链接 / 分享 / 拍照 / 纯文本四种导入；全屏逐步引导 + 内置计时器 + 灵动岛 / 锁屏 / Apple Watch；常备食材记忆
  • 短板评分人数仅 16（早期产品）；定位是私人菜谱本，无公开内容库、无审核发布态、无「被遗忘细节」概念
  • 启示跟做体验（大字 / 免触控 / 锁屏）已是这类产品的标准配置；我们若只在小程序做计时器，体验上会落后，需把「免触控 + 锁屏 / 订阅消息」纳入路线

Coozi

A+B 级
中国区版本 v1.0.8评分 4.147 人评分更新 2026-10-18

定位 家庭做饭场景的 AI 厨房助手：链接转菜谱 → 周计划 → 买菜清单 → 跟做 → 烹饪记录。

  • 强项来源快速扩张（2026 年 10 月连发版本，加入快手、头条）；大字步骤、语音计时、手势翻页；烹饪记录可写照片 / 评分 / 心得 / 实际用量
  • 短板评分人数仅 7，仍属早期；「实际用量」是私人笔记，未结构化、不可检索、不进入公开内容库
  • 启示「做完之后记录我改了什么」是通向「被遗忘细节」的最近一步，但竞品都停在私人笔记层。把它做成可审核、可复用、可精选的公开字段，就是我们的切口

ReciMe

A+B 级
美区版本 v8.3.1评分 4.7933.9 万 人评分更新 2026-11-14

定位 品类标杆。2021 年上线时是食谱社交 App，2023 年砍掉全部社交功能，只围绕「从社媒导入食谱」重做。

  • 强项导入 → 份量调整 → 周计划 → 按超市分区的购物清单 → 部分地区下单 → 卡路里，形成用餐规划系统；第三方估算月流水约 278 万美元、用户约 1,500 万（非审计）
  • 短板差评集中在长视频导入慢、闪退、订阅贵；官方承认评论区里的完整做法未必能读到、一条视频讲三道菜可能只识别一道
  • 启示① 单点导入留不住人，必须往上下游延伸；② 「社交」在这个品类被验证是伪需求，我们架构里不做社区 feed 的判断是对的；③ 准确性仍是全行业短板

Pluck

A+C 级
美区版本 v1.1评分 4.002 人评分更新 2026-10-12

定位 多模态（L3）视频转菜谱：关键帧 + 音频 + 屏上文字 + 字幕 + 描述，冲突时互相校正。

  • 强项公开把技术分层讲清楚：L1 只读文案 / L2 文案 + 音频转写 / L3 多模态融合；强调「视频没给的用量写未标注，不拿常识冒充事实」
  • 短板评分人数仅 2，产品非常早期；官网博客带明显自家对比倾向，功能描述需打折看
  • 启示「先取证，再成卡」与「不确定就写未标注」直接印证我们架构文档里解析 JSON Schema 的 evidence_timestamp / confidence / uncertainties 三个设计，应保留并加进审核台 UI

SideChef（晒厨易）

A+B 级
美区版本 v3.5.2评分 4.7023 人评分更新 2019-03-25

定位 手把手分步引导：每一步配图 / 视频、语音指令免触控、内置计时器、可购物菜谱与智能厨电联动。

  • 强项把「Cook with Me」做成完整交互；商店描述标 12,000+ 步骤图西餐食谱；免费核心功能保留

Kitchen Stories

A+B 级
美区版本 v27.6.0评分 4.822.3 万 人评分更新 2026-11-04

定位 编辑制精品菜谱 + 高质量技巧视频，强调「为什么这么做」而不仅是「做什么」。

A 级
美区版本 v3.41评分 4.9143.3 万 人评分更新 2026-10-08

05

五个关键发现

每条都注明证据来源与等级，便于回查。

1

视频转菜谱已是品类，解析能力不是护城河

海外 ReciMe 在 2023 年砍掉社交、只做「社媒视频 → 结构化菜谱」后，订阅与收入增长约 20 倍（团队自述）；中文侧谱提覆盖 9 个平台、Coozi 覆盖 6 个并持续扩张、口袋厨神会为每一步自动截取视频对应画面。开源侧已有「RC 食卡」「recipe-from-video」等方案，用 Whisper / 火山 ASR + DeepSeek 就能跑通，门槛降到单人周末可完成。结论：P3 再自研一套完整解析引擎，投入产出比很差。

证据：36 氪 / 白鲸出海 ReciMe 报道（B）、Pluck 技术分层博客（C）、谱提与 Coozi 商店描述（A）、开源项目说明（C）
2

「记忆里的美食」有真实需求，但现有形态是话题标签与私人记录本

下厨房官网「妈妈的味道」专题 2,316 件作品、「家乡的味道」625 件，说明情感 UGC 供给确实存在；「味觉记忆馆」把痛点写得极准——长辈年迈 / 离世后「全凭手感」的细节随之消失；「家传菜谱博物馆」甚至是无代码平台几分钟生成的Demo。但它们都把记忆当成一段文字 / 一张照片 / 一个话题，没有把「不能省的那一下」抽成字段。

证据：下厨房官网专题页作品数（A）、TRAE 社区概念稿与今日头条个人文章（C，仅证明需求存在，不代表商业产品）
3

计时器是标配，且单计时器与多灶场景存在冲突

下厨房烹饪模式、豆果智能定时、谱提内置计时器 + 灵动岛 / 锁屏 / Apple Watch、Kitchen Stories 引导模式、拿手菜小本本一步一屏到点震动都有。更值得注意的是云小厨与拿手菜小本本做的是多道菜并行、各自停在当前步、各自计时——这对应中国家庭「一荤一素一汤同时开火」的真实场景。我们原型 v4 为降低压力感改成「全页唯一计时器」，方向与市场主流相反。

证据：各产品公开功能描述（A/B）、公众号对开源小程序「拿手菜小本本」的功能拆解（C）
4

真正的空白在内容模型层：细节实体 + 审核发布

竞品里最接近的是 Coozi 的「烹饪记录：实际用量 / 心得」、懒饭的「关键步骤防错贴士」、Kitchen Stories 的「How-To 技巧视频」，以及下厨房评论区的实操贴士。它们共同的短板是：自由文本、绑在私人记录或评论区里、不可按类型检索、不可精选、无来源与置信度、无审核态。把 forgotten_details 做成独立表并接上生产管线与投稿审核，是矩阵里唯一整列空白的两项之一。

证据：功能对标矩阵（基于公开资料整理，A/B/C 混合，未实机验证）
5

小程序路线可行且便宜，但合规与准确率是两个硬约束

「拾味记」公开的技术栈是腾讯云 ASR + Moonshot Kimi + 云开发异步队列，抖音无官方接口、需第三方解析客户端，LLM 调用约 20–30 秒因此云函数超时要调到 60 秒。同时，几乎所有视频转菜谱产品都在官网写明「AI 可能遗漏，下厨前请核对用量」；Pluck、RC 食卡更进一步要求「视频没给的用量明确写未标注，不拿常识冒充事实」。准确率的诚信设计与内容安全审核，必须写进产品而不是留给提示词。

证据：拾味记独立开发者技术说明（C）、一键大厨官网 FAQ（A）、Pluck / RC 食卡方法说明（C）
06

机会、风险与需要拍板的问题

把「能做什么」和「可能死在哪」放在一起看。

机会

内容模型差异「被遗忘细节」作为独立实体，可检索、可精选到发现页、可投稿、可审核、可统计，是矩阵里唯一整列空白
供给已被验证下厨房情感专题 2,316 件作品证明 UGC 愿意讲家里的做法，冷启动不必全靠编辑凭空写
生产管线可借力ASR / 解析 / LLM 均有成熟现成能力与低成本云开发路径，把资源集中在审核与结构化层
小程序低门槛免安装、分享链接跳转顺滑，适合「家人发来一条视频 / 一段语音」的传播场景
不做社区是对的ReciMe 砍掉社交后增长 20 倍，垂直社区又被小红书 / 抖音持续分流，避免重投入做 feed

风险

差异化可被低成本复制「妈妈的味道」这类话题标签大厂一天就能加；护城河必须落在长期积累的结构化细节数据与审核标准上，而非一句定位
解析来源合规抖音 / 小红书无官方开放接口且反爬策略变化；须坚持授权 / 自制 / 用户主动分享，不写爬虫，并准备可切换的解析后端
准确率与信任用量、火候、时长解析错会直接毁掉信任；必须做「可核对」设计、原始转写留痕、不确定项显式留空
UGC 内容安全小程序公开 UGC 需内容安全校验 + 人工审核 + 举报入口，否则上架与运营都有风险
付费意愿国内小程序生态偏免登录 / 免费；ReciMe 的订阅成功不能直接外推到中文市场
冷启动内容缺口现有原型 12 菜 58 步，但材料 0 条、遗忘细节 0 条、故事 0 篇——主打内容一条都没有

需要拍板的三个问题

① 单计时器还是多菜并行？ 建议保留单计时器作为默认（延续低压力感、视觉主次清晰的结论），但把「多菜并行」列为 P2 可选模式，并用一次真实下厨场景验证，而不是现在就下结论。

② 解析自研还是接入？ 建议 P3 不自研 ASR / 抽帧，改为「接入现成解析能力 + 自建审核台与遗忘细节抽取」，把工程预算移到内容质量。

③ 内容从哪来？ 建议 P0 不走纯人工补录，改为「编辑少量样板（约 20 道）+ 定向 UGC 征集 + 人工结构化审核」并行，先验证「细节」这个内容单元能否被用户理解和贡献。

对现有架构方案的修订建议

对应 plans/记忆里的美食-主体架构方案.md 与 plans/记忆里的美食-数据模型设计.md。本节是建议，尚未改写那两份文档。

#原方案位置与内容调研发现建议修订优先级
R1§5 / P3：自建「转存 → ASR + 抽帧 → LLM 结构化」完整管线解析已是成熟品类，中文小程序与开源方案门槛极低；成本可趋近于零P3 收缩为「接入现成 ASR / 解析能力 + 自建审核台 + 遗忘细节抽取」；parse_jobs 保留但不再自建媒体预处理模块高
R2§1 定位：「记忆里的美食 / 被遗忘的步骤」作为差异化情感叙事已有话题标签与家传记录本产品，容易复制差异化表述收敛为「结构化细节实体 + 公开可检索 + 审核发布」，明确不与私人菜谱本竞争；§9 风险表补一条「被话题标签低成本复制」高
R3§3.1 做菜模式：全页唯一聚焦计时卡市场主流含多菜并行独立计时，对应双灶场景默认保留单计时器；把「多菜并行计时」列入 P2 可选项并做一次用户验证；数据模型 cook_sessions.state 已用 JSONB，可容纳多菜状态，无需改表中
R4§3.1 跟做交互：计时 + 到点提醒免触控（语音 / 手势 / 锁屏 / 灵动岛）已是同类标配P1 补「订阅消息到点提醒」与「屏幕常亮」；长期评估语音翻步；不引入 WSS（平台固定网关不注册 socket 域）中
R5§8 / P0：人工补录约 100 条材料 + ≥36 条细节下厨房情感专题 2,316 件作品证明 UGC 供给存在改为「编辑样板 20 道 + 定向 UGC 征集 + 人工结构化审核」；先定义「什么算一条合格的遗忘细节」的审核标准，再放量高
R6数据模型 §7 解析输出 JSON SchemaPluck / RC 食卡公开方法印证「先取证、不确定写未标注」Schema 保持不变，但把 evidence_timestamp / confidence / uncertainties 显式做到审核台 UI；解析失败或不确定时 default_seconds 必须留空，不允许模型猜测高
R7§0 后台形态 A（同应用 + 平台数据管理面板）同类小程序多为单人云开发，更不应拆库结论不变；但 P3 若评估微信云开发方案，需重新核对「单应用单环境」约束，避免引入第二套数据源低
