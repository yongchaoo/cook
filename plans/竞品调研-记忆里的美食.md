## 0. 结论先行

**产品主体判断成立，但差异化落点必须换。**

1. 「查看菜谱 + 材料清单 + 投稿 + 管理后台 + 数据库」是行业标配，不构成差异；「记忆叙事」「视频解析」「计时器」三条线也分别已有大量玩家。**真正没人做的，是把「被遗忘的关键细节」抽象成独立、可检索、可审核、可精选的结构化内容实体**，并让它同时连接内容生产管线与 UGC 投稿。差异在**内容模型层**，不在功能层。
2. **视频转菜谱已从「设想」变成 2026 年成熟品类。** 海外 ReciMe 被第三方估算月流水约 278 万美元、用户约 1,500 万；中文侧谱提 Pullit、Coozi、口袋厨神、一键大厨、拾味记等已覆盖抖音 / 小红书 / B站，开源方案门槛低到单人周末可完成。自研解析引擎不再是壁垒。
3. **「记忆里的美食」情感切口也不是空白。** 下厨房官网「妈妈的味道」专题 2,316 件作品、「家乡的味道」625 件；已有「味觉记忆馆」「家传菜谱博物馆」「食遇日记」等做家传菜谱、语音录制、味道日记。但它们都是**话题标签 / 私人记录本**形态，不是「公开可检索的结构化内容库 + 审核发布」。
4. **计时器是标配，且我们的「单计时器」结论与市场主流方向相反。** 下厨房烹饪模式、豆果智能定时、谱提内置计时器 + 灵动岛 / Apple Watch、Kitchen Stories 引导模式、拿手菜小本本一步一屏都已具备；云小厨、拿手菜小本本做的是**多菜并行、各自独立计时**，对应真实双灶场景。原型 v4 基于「降低压力感」选单计时器，是 UX 判断而非功能优势，需单独验证。
5. **微信小程序形态已被验证可行且成本极低。** 「拾味记」用腾讯云 ASR + Moonshot Kimi + 云开发异步队列实现视频转菜谱，公开描述称按量计费成本趋近于零。这支持架构方案 A 路线，也意味着冷启动速度比技术本身更关键。

### 三个被推翻的原假设

| 原假设（上一版架构方案） | 调研结论 |
|---|---|
| P3「视频 → 材料与步骤」是后续创新点 | 已是红海初现，应改为接入现成能力 |
| 「记忆 / 家传菜谱」是独有定位 | 已有多家在做，须收敛到「结构化细节」 |
| 单一聚焦计时器是体验优势 | 是取舍不是优势，多灶场景存在缺口 |

### 仍然成立的三条架构判断

- 管理后台不做第二个云应用（单环境单库）依然正确；同类小程序多为单人云开发，更不该拆库。
- 「被遗忘的细节」独立成表、独立审核的设计依然是空白点。
- 数据库单一事实源 + 小程序只读 `published` 的内容发布模型，在竞品里普遍缺失（多数是私人记录本，没有审核发布态）。

## 2. 赛道格局：三条线，一个空白区

以「内容结构化 / 自动化程度」×「情感记忆浓度」定位：

| 类型 | 代表产品 | 解决什么 | 缺失 |
|---|---|---|---|
| ① 内容库存型 | 下厨房、豆果、香哈、美食杰、懒饭 | 菜谱量、分类检索、社区 | 流量被抖音 / 小红书分流；变现靠广告与电商且多次受挫；无结构化细节 |
| ② 视频转菜谱型 | ReciMe、谱提、Coozi、口袋厨神、Pluck、一键大厨 | 「收藏 → 上桌」 | 增长最快、付费模型最清晰；但准确率是普遍短板，且不处理情感 / 记忆 |
| ③ 家传记忆型 | 味觉记忆馆、家传菜谱博物馆、食遇日记、下厨房情感专题 | 家传菜、语音录制、味道日记 | 情感浓度高，但形态是话题标签或私人记录本，缺结构化与公开检索 |

**空白区**：把「高结构化」与「高情感记忆」同时做到，且带内容审核与发布态、面向公开内容库而非私人本——象限右上没有对应产品。

## 5. 五个关键发现

1. **视频转菜谱已是品类，解析能力不是护城河。** ReciMe 2023 年砍掉社交、只做「社媒视频 → 结构化菜谱」后，订阅与收入增长约 20 倍（团队自述）；谱提覆盖 9 平台、Coozi 覆盖 6 个并持续扩张、口袋厨神为每步自动截取视频画面。开源侧「RC 食卡」「recipe-from-video」用 Whisper / 火山 ASR + DeepSeek 即可跑通。**P3 再自研完整解析引擎，投入产出比很差。**
2. **「记忆里的美食」有真实需求，但形态是话题标签与私人记录本。** 下厨房情感专题 2,316 件作品证明 UGC 供给；「味觉记忆馆」把「长辈全凭手感、细节随人而去」的痛点写得极准；「家传菜谱博物馆」是无代码平台几分钟生成的 Demo。共同短板：**把记忆当成一段文字 / 一张照片 / 一个话题，没有把「不能省的那一下」抽成字段。**
3. **计时器是标配，且单计时器与多灶场景冲突。** 详见结论第 4 条。原型 v4 的「全页唯一计时器」方向与市场主流相反。
4. **真正的空白在内容模型层。** 最接近的是 Coozi 的「烹饪记录：实际用量 / 心得」、懒饭「关键步骤防错贴士」、Kitchen Stories「How-To 技巧视频」、下厨房评论区实操贴士。共同短板：自由文本、绑在私人记录或评论区、不可按类型检索、不可精选、无来源与置信度、无审核态。`forgotten_details` 独立表 + 生产管线 + 投稿审核是矩阵里唯一整列空白的两项之一。
5. **小程序路线可行且便宜，但合规与准确率是硬约束。** 拾味记技术栈（腾讯云 ASR + Kimi + 云开发异步队列，抖音无官方接口需第三方解析、LLM 20–30 秒故云函数超时调至 60 秒）可作基准；几乎所有同类产品官网都写「AI 可能遗漏，下厨前请核对用量」，Pluck / RC 食卡更进一步要求「视频没给的用量明确写未标注，不拿常识冒充事实」。**准确率的诚信设计与内容安全审核必须写进产品，而不是留给提示词。**

## 6. 机会、风险与待拍板

### 机会

- 内容模型差异：细节实体可检索 / 精选 / 投稿 / 审核 / 统计，矩阵里唯一整列空白。
- 供给已验证：下厨房情感专题 2,316 件作品，冷启动不必全靠编辑凭空写。
- 生产管线可借力：ASR / 解析 / LLM 均有成熟能力与低成本云开发路径。
- 小程序低门槛：免安装、分享链接跳转顺滑，适合「家人发来一条视频 / 一段语音」。
- 不做社区是对的：ReciMe 砍社交后增长 20 倍，垂直社区又被小红书 / 抖音持续分流。

### 风险

| 风险 | 说明 |
|---|---|
| 差异化可被低成本复制 | 「妈妈的味道」这类话题标签大厂一天就能加；护城河必须落在长期积累的结构化细节数据与审核标准 |
| 解析来源合规 | 抖音 / 小红书无官方开放接口且反爬变化；坚持授权 / 自制 / 用户主动分享，不写爬虫，准备可切换后端 |
| 准确率与信任 | 用量 / 火候 / 时长解析错直接毁信任；需可核对设计、原始转写留痕、不确定项显式留空 |
| UGC 内容安全 | 小程序公开 UGC 需内容安全校验 + 人工审核 + 举报入口 |
| 付费意愿 | 国内小程序生态偏免登录 / 免费；ReciMe 订阅成功不能直接外推 |
| 冷启动内容缺口 | 现有原型 12 菜 58 步，但材料 0 条、遗忘细节 0 条、故事 0 篇 |

### 需要拍板的三个问题

1. **单计时器还是多菜并行？** 建议保留单计时器为默认，把「多菜并行」列为 P2 可选并做一次真实下厨验证；数据模型 `cook_sessions.state` 为 JSONB，已可容纳多菜状态。
2. **解析自研还是接入？** 建议 P3 不自研 ASR / 抽帧，改为「接入现成解析 + 自建审核台与遗忘细节抽取」。
3. **内容从哪来？** 建议 P0 不走纯人工补录，改为「编辑样板约 20 道 + 定向 UGC 征集 + 人工结构化审核」，先验证「细节」这个内容单元能否被用户理解和贡献。
