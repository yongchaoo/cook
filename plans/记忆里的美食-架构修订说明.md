## 0. 结论先行

**主体架构不用推倒重来，但要改三条实现路径、补四项缺失定义。**

调研没有推翻「结构化内容库 + 内容生产管线 + 双端」这个主体判断，也没有推翻单库、单环境、`forgotten_details` 独立成表这些核心设计。它推翻的是三件具体做法：

| 原做法 | 调整后 |
|---|---|
| P3 自建「ASR + 抽帧 + LLM」完整解析管线 | **接入现成解析能力**，自研范围收缩到「遗忘细节抽取 + 人工审核台」 |
| 以「记忆 / 被遗忘」这句定位作为差异化 | 收敛为**结构化细节实体 + 公开可检索 + 审核发布**，并补一份「什么算合格细节」的审核标准 |
| P0 人工补录约 100 条材料 + 36 条细节 | 改为**先定审核标准 → 编辑样板 20 道 → 定向 UGC 征集 → 人工结构化审核** |

另外一项是交互取舍的修正：单计时器从「唯一方案」降级为「默认方案 + P2 可选多菜并行」。

**总计：7 项调整、4 项新增、6 项坚持不变。其中 4 项高优先级会改变后续开发计划，3 项需要你拍板。**

## 2. 逐项调整（含可直接替换的文本）

### A1 · 差异化表述收敛

**原设计（方案 §1.1）**：定位为「把那些没被写进菜谱、只留在家里人手上和记忆里的做菜细节，结构化地留下来」，差异化栏写「常规菜谱写做什么，本产品补为什么这一步不能省」。

**问题**：这句话本身已被多个产品用话题标签或私人记录本实现。下厨房「妈妈的味道」专题一天就能复制一句 slogan，但它没有复制的是「可检索、可审核、可发布的结构化实体」。

**调整后文本（替换 §1.1 定位表「差异化」与「明确不做」两行）**：

| 维度 | 新表述 |
|---|---|
| 差异化 | 不是「有情感故事」，而是把「不能省的那一下」做成**独立、带类型与来源、带置信度、可检索、可精选、可审核发布**的内容实体；产品对象是**公开内容库**，不是私人菜谱本、不是社区话题 |
| 明确不做 | 不做私人菜谱本 / 家庭共享空间（味觉记忆馆、食遇日记、拿手菜小本本已覆盖）；不做社区 feed 与关注流（ReciMe 反证）；不做短视频播放；不做电商带货；不做 AI 生成菜谱直接发布 |

**影响**：§0 第 4 条判断、§9 R9 风险条目需同步改写；§3.1 详情页「第 2 段最高视觉权重」保持不变，但强调它是**结构化字段的展示位**，不是故事墙。

**验收**：随机抽 10 条「遗忘细节」，每条都能回答「类型 / 挂哪一步 / 为什么重要 / 从哪来 / 谁审核的」，且能被类型筛选检索到。

### A2 · 新增「什么算一条合格的遗忘细节」审核标准

**原设计**：§1.1「内容单元」只写了「被遗忘的细节」这个名词，数据模型 §3.7 只有字段，**没有判定标准**。这会导致 UGC 征集收上来一堆「少放点盐更好吃」这类口味偏好，把产品差异点稀释掉。

**调整后新增（方案 §1.1 后插入「1.3 遗忘细节的准入标准」）**：

一条内容要进入 `forgotten_details`，必须同时满足 5 条：

1. **影响成败而非口味偏好**：少了它会做失败或明显走样（如「焯水后必须过冷水，否则余温会让肉继续变老」），不是「我喜欢更辣」。
2. **可复现**：是具体动作、顺序、火候、水量、时间点或参数，能被另一个人照着做。
3. **有解释**：`why_it_matters` 必须填，说明为什么这一步不能省。
4. **可归属**：能挂到某个 `step_id`，或明确标注为「全菜通用原则」（如全程不盖锅盖）。
5. **有来源且未被编造**：`source_type` 必填；解析产物必须附 `evidence_timestamp` 与 `confidence`；**模型推测出来的、视频里没有的内容一律不进表，写进 `uncertainties`**。

反例（应驳回或转到「记忆故事」）：「奶奶做的红烧肉最好吃」「小时候过年才吃得到」「我觉得糖放多了」。

**影响**：审核台 UI 需要按这 5 条做逐项勾选；投稿表单「家里多做的那一步」输入框要给这 5 条做占位提示；§6 投稿闭环增加「不合规转记忆故事」分支。

**验收**：抽 30 条 UGC 提交，两名审核者按标准独立判定，一致率 ≥ 80% 才算标准可用；低于此值先修标准再放量。

### B1 · 视频解析从自建改为接入

**原设计（方案 §2 组件清单 M7/M8、§5.2 五段链路、§8 P3）**：M7「视频预处理：转存、ASR、抽帧、切片」与 M8「任务编排：解析任务状态机、重试、人工卡点」均列为自建；P3 验收为「≥30 道抽样出质量报告」。

**问题**：这五项能力平台都不提供，且市场上已有成熟供给（腾讯云 ASR + LLM 的云开发方案、Video2Recipe 类 REST API、开源 Whisper 管线）。「拾味记」公开描述称云开发按量计费成本趋近于零。自建等于用最高成本重做一件已商品化的事。

**调整后文本（替换 §5.2 链路表）**：

| 段 | 输入 | 输出 | 归属 | 人工卡点 |
|---|---|---|---|---|
| ① 来源登记 | 用户分享链接 / 运营登记授权素材 / 自制视频 | `video_sources` 记录（含 `source_type`、`license_note`、`attribution`） | **自建** | **必须**：确认来源可用、不侵权 |
| ② 提交解析 | 来源记录 | 外部解析任务（`provider` + `provider_job_id`） | **接入** | 失败重试，保留原始返回 |
| ③ 结构化抽取 | 外部返回的转写文本 + 关键帧描述 | 材料 / 步骤 / **遗忘细节** / 置信度 / 不确定项 JSON | **自建（核心）** | **必须**：LLM 输出只作草稿 |
| ④ 逐字段审核 | 草稿 JSON | 校对后的正式记录 | **自建（核心）** | **必须**：按 A2 五条标准逐条判定 |
| ⑤ 发布 | 审核通过 | `published` + `version+1` + `publish_log` | **自建** | 记录审核人 |

**M7 / M8 调整**：M7 从「自建」改为「外部服务（可切换供应商）」；M8 从「自建队列」降级为「`parse_jobs` 状态表 + 回调/轮询 + 人工触发」，不引入独立调度系统。

**新增约束**：
- 解析供应商必须**可切换**：`provider` 字段隔离，业务层不直接耦合任何一家 SDK；抖音 / 小红书无官方开放接口且反爬策略会变，须准备至少一条备用路径。
- 坚持「授权 / 自制 / 用户主动分享」，**不写爬虫**，与 v1.0 §5.3 合规边界一致。
- 若 P3 评估微信云开发方案，需重新核对「单应用单环境」约束，避免引入第二套数据源（§0 取舍表 R7 结论不变）。

**影响**：§7.1 能力边界表「外部服务」列改为「接入」；§8 P3 交付物去掉「转存 / ASR / 抽帧」；数据模型 §3.12 `parse_jobs` 增加供应商字段（见 C1）。

### B2 · 准确率从 Schema 约束升级为产品硬规则

**原设计**：数据模型 §7 解析输出 JSON Schema 已包含 `evidence_timestamp`、`confidence`、`uncertainties`，设计方向正确（Pluck / RC 食卡的公开方法也印证「先取证、不确定写未标注」）。但它只约束了数据格式，没有约束**审核台怎么展示**和**产品怎么兜底**。

**调整后新增三条硬规则**：

1. **不确定必须留空**：`steps.default_seconds` 在视频未明确给出时长、或解析置信度低于阈值时，**必须为 NULL**，禁止模型用常识猜一个 10 分钟；由运营在审核时补。
2. **审核台必须可见三类证据**：每条解析结果旁显示 `evidence_timestamp`（可跳到对应时间点）、`confidence`、`uncertainties` 原文；原始 `transcript` 与 `raw_llm_json` 永不覆盖。
3. **草稿永不可直发**：任何解析产物只能落在 `status = 'draft'`，必须经人工逐字段确认才能进入 `published`；RLS 已保证草稿对小程序不可见（模型 §5.2）。

**新增指标口径（重要）**：P3 质量指标必须拆成两层，避免把第三方能力算成自己的成绩——

| 指标层 | 定义 | 归属 |
|---|---|---|
| 供应商基础准确率 | 外部解析返回的「材料条数 / 步骤顺序」与人工标注的一致率 | 第三方，**用于选供应商，不作为我方产品成绩** |
| 我方增量准确率 | `forgotten_details` 被审核保留率、`why_it_matters` 有效性、A2 五条标准通过率 | 自建，**这才是核心价值指标** |

调研报告 §5.4 的「遗忘细节命中率 ≥60%」目标值保留，但明确为**我方增量指标**，且标注「设计目标、当前无实测数据」。

### D1 · 单计时器降级为默认方案

**原设计（方案 §3.1）**：「沿用单一聚焦计时卡，一次一个计时器，不自动开下一步」；术语表把「做菜模式」定义为「一次只显示一个计时器」。

**问题**：云小厨、拿手菜小本本做的是「多道菜并行、各自停在当前步、各自计时，到点写明是哪道菜的第几步」，对应中国家庭「一荤一素一汤同时开火」的真实场景。我们基于「降低压力感」选择单计时器，是 UX 判断，不是功能优势；把它写成唯一方案会留场景缺口。

**调整后文本（替换 §3.1 做菜模式行与附录 B 术语）**：

> 做菜模式默认为**单聚焦计时卡**（延续原型 v4–v7 的低压力感与视觉主次结论），一次只显示一个计时器，完成/跳过后不自动开始下一步。P2 增加可选的「多菜并行」模式：按菜切换、每道菜停在当前步、各自独立计时、到点提示注明「哪道菜的第几步」。`cook_sessions.state` 用 JSONB 承载多菜状态，无需改表。上线前用一次真实双灶下厨场景验证两种模式的取舍。

**验收**：原型 HTML 不动；仅在小程序实现阶段保留两种模式的交互稿，先做用户验证再定 P2 是否上线。

### D2 · 跟做体验补齐免触控与后台提醒

**原设计（方案 §7.2）**：计时器条目已写「`endAt` 时间戳 + `wx.setStorage` 落盘，`onShow` 重算；后台到点提醒需走订阅消息」。方向正确，但没有列为 P1 交付。

**调整后（§8 P1 交付列补充）**：
- P1 必做：订阅消息到点提醒、屏幕常亮（`wx.setKeepScreenOn`）、计时状态 `endAt` 落盘与 `onShow` 重算。
- 长期评估：语音翻步（谱提 / Coozi / SideChef 已把它做成标配）。
- **明确不引入 WSS**：平台固定网关只服务 HTTPS，未注册 socket 域（§7.2 约束），不做实时多端同步。

### E1 / E2 · 阶段路线重排与指标拆分

**原方案（§8）**：P0 内容建模（12 菜 + 100 条材料 + 36 条细节）→ P1 消费端 → P2 UGC → P3 视频管线 → P4 后台升级。

**调整后**：

| 阶段 | 目标 | 交付 | 验收口径 | 依赖 |
|---|---|---|---|---|

## 4. 坚持不变（六条，避免误读）

1. **单应用、单环境、单库**：管理后台不做第二个云应用，「数据库同步」靠同库一致性而非跨库 ETL（调研中同类小程序多为单人云开发，更不该拆库）。
2. **数据库为唯一事实源**：小程序只读 `status = published`，草稿 / 解析中间态永不对端上可见，端上不降级到 `localStorage`。
3. **RLS 三类分权**：公开内容读 published / 用户数据 owner-only / 内部表 server-only；两道闸门（GRANT + POLICY）同时具备。
4. **`forgotten_details` 独立成表**：这是功能矩阵中唯一整列空白的两项之一，不能退回 `steps.tip` 字段。
5. **投稿走 `submissions.payload(JSONB)` 审核缓冲层**：端上永不直接写正式表，审核通过后才归并。
6. **不做社区 feed**：ReciMe 2023 年砍掉社交后订阅与收入增长约 20 倍（团队自述），且垂直社区持续被小红书 / 抖音分流。

平台硬约束同样不变：`appType: "miniprogram"` 创建时一次性写入、小程序 SDK 用 `/miniprogram` 子路径并传齐 `publicConfig` 两项、禁止手写 `wx.request` 打 `/.cloud/**`、`app.json` 含 `lazyCodeLoading: "requiredComponents"`、代码定稿后生成隐私清单、`docs/wxamp-info.md` 的 AppSecret 不进代码。

## 5. 调整后的主体骨架

```text
来源（用户分享 / 授权视频 / 家人口述 / UGC 投稿）
  ↓ 登记授权与署名（自建）
外部解析服务（可切换供应商，非自建）
  ↓ 转写文本 + 关键帧描述 + 原始返回留痕
我方结构化层（核心自建）
  ├─ 材料 / 步骤 / 时长（不确定项留空）

  ↓

  ↓

  ├─ 微信小程序：只读 published · 三段式详情 · 默认单计时器（P2 可选并行）
```

## 9. v1.2 决策落定（2026-11-18 14:32）

> **决策原文**：「接入；只有官方发布的才需要审核，个人用户不需要审核，审核也是内部自己审核；标准+样板+UGC」
> **本节优先级最高**，覆盖 v1.0 / v1.1 中所有冲突表述。前文完整保留以便回退。

### 9.1 解释口径（先对齐，避免歧义）

「个人用户不需要审核」按以下口径落地：用户自己创建 / 导入 / 保存的内容属于**个人私有域**，仅本人可见，因此**不进入人工审核队列、不带审核状态**；只有**要进入官方公开库**的内容（编辑发布、外部解析产出、用户主动贡献）才需要审核，且审核由**内部运营**完成，不对外暴露流程。

这不是免除内容安全：公开可见的 UGC 仍需机器内容安全检测 + 举报入口（§9.4）。若你原意是「连投稿进公开库也不审核」，请指出——那会与微信小程序的内容安全要求冲突，我会改为「不做人工审核、但保留机器检测 + 举报」的折中方案。

### 9.2 三项决策生效表

| 决策 | 结论 | 生效范围 | 覆盖的旧表述 |
|---|---|---|---|
| **接入** | 视频解析接入现成服务，供应商可切换；自研只做「遗忘细节抽取 + 内部审核台 + 发布」 | §2 M7/M8、§5、§8 P3；数据模型 §12 增量字段全部生效 | B1 由「建议」变「定案」；删除自建 ASR / 抽帧 / 转存 / 调度 |
| **审核模型** | 只有官方发布内容需审核，且**内部自己审核**；个人用户私有内容不审核 | 新增三层内容域，改写状态机适用范围、投稿闭环、RLS | v1.0 §4.2 / §6 / §9 R5；v1.1 A2 适用范围（见 §9.5） |
| **标准 + 样板 + UGC** | 先定 A2 五条标准 → 编辑样板 20 道 → 定向 UGC 征集 → 内部审核后发布 | §8 P0 | E1 由「建议」变「定案」 |

### 9.3 三层内容域（本次最大改动）

| 域 | 产生者 | 可见范围 | 审核 | 承载 |
|---|---|---|---|---|
| **A 官方公开** | 编辑 / 运营录入、外部解析产出、UGC 征集采纳 | 全体小程序用户（仅 `published`） | **内部审核（必做）**，完整状态机在后台 | `dishes` / `steps` / `dish_ingredients` / `forgotten_details` / `dish_media` |
| **B 个人私有** | 用户自己创建 / 导入 / 保存的菜谱与记录 | **仅本人**（RLS owner-only） | **无审核、无审核态、无 `status` 字段** | **新增 `personal_recipes`**（JSONB，见数据模型 §13.2） |
| **C 投稿通道** | 用户主动点「贡献到公开菜谱」 | 本人 + 内部审核台 | 机器内容安全 + **内部审核** | `submissions`（语义收窄，见 §13.4） |

**「审核也是内部自己审核」四条落地规则**：

1. 审核台只对 `is_admin()` 开放，端上无审核入口、无审核状态机 UI。
2. 投稿者只看到「已收到 / 已收录」两态，不暴露 `reviewing / rejected` 细节；驳回可给一句人话理由。
3. 完整状态机（`draft → reviewing → published / archived`）保留在后台侧，只服务 A 域与 C 域。
4. 不做社区互审、用户投票、公开审核队列（与「不做社区 feed」一致）。

### 9.4 一条必须保留的合规边界

微信小程序对**公开可见的 UGC** 有内容安全要求。B 域内容仅本人可见时不触发人工审核；但一旦提供分享卡片 / 图片 / 链接给他人，就构成公开传播，必须接入内容安全检测 + 举报入口。**这是平台底线，不是「内部审核」，与决策不冲突。** 设计上 B 域默认不提供分享入口；若后续增加分享，先补机器校验并把该行为纳入 C 域管理。

### 9.5 A2 五条标准的适用范围收窄

A2 从「所有 UGC 的审核标准」收窄为「**官方发布内容与投稿采纳的编辑标准**」。个人私有内容不受约束——用户想在自己的本子里记「奶奶做的最好吃」完全自由。

**P0 的 UGC 征集走 C 域**：征集来的内容要成为官方发布内容，因此仍需按 A2 结构化后由内部审核采纳。这与「个人用户不需要审核」**不矛盾**——区别在于「自己留着」还是「贡献到公开库」。
